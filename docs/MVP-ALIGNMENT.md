核查日期：2026-09-22。本文为工程研究与改进记录，不是正式申报书或主办方验收意见。

## 1. 优先依据本期规则

[九月黑客松官网](https://moonbitlang.github.io/Hackathon2026/)要求：MoonBit为主要实现语言、
公开可追踪开发记录、README、可运行示例及必要测试、实质工作、开源来源说明，以及
参赛者能解释目标、路径和质量。官网FAQ明确项目可以不大，重视清晰边界、可靠测试、
完整文档和实际可用性。因此我们选择把标量求根的小范围做完整。

不少于10次有效commits的要求来自参赛者此前提供的正式表单第8条；这是一项赛事要求，
不是通用MVP定义。有效性及本项目范围仍由主办方审核。早期SCC或OSC活动中的代码规模、
提交数量或奖励口径不能直接移植为九月赛的门槛。完整飞书章程此前读取受限，本次未将
通用MVP概念当作取代章程的依据。

官网另有“MoonBit MVP计划”，展开为Most Valuable Professional，属于人员计划；
它与驳回通知中产品的Minimum Viable Product是不同语境。

## 3. “比较公认的MVP标准”如何使用

[Agile Alliance的MVP词条](https://agilealliance.org/glossary/mvp/)强调以尽量小的投入，
从实际用户行为中取得经过验证的认识，并指出“功能最少”本身不足以构成正确的MVP实践。
[The Lean Startup方法说明](https://theleanstartup.com/principles)同样以构建、衡量、学习为循环，
先验证要解决的问题，再根据反馈调整。它们提供的是产品验证方法，不是统一代码行数、
算法数、页面数或测试数标准；该方法也不保证通过具体比赛。

所以本项目需分别判断：**工程上是否可供别人使用**，以及**真实使用是否支持价值假设**。
目前前者已有可复现证据，后者尚无真实用户反馈。准确定位是“可试用的工程MVP，
需求验证待完成”，不宜宣称已经验证市场需求。

## 4. 我们采用的对齐目标与状态

以下为我们自己制定的检查目标，非官方新增门槛。

| 目标 | 判定方法 | 2026-09-22 状态 |
|---|---|---|
| 清晰用户与用途 | MoonBit开发者在连续标量模型中反求参数，并决定如何处理停止结果 | 已定义；真实需求待验证 |
| 完整核心流程 | 自定义函数 → 配置区间/容差/预算 → 求解 → 检查状态 → 导出 | 已实现并测试 |
| 外部工程可复用 | 另一模块不访问私有函数，使用两种算法、扫描、导出及错误类型 | 本轮新增，3项消费模块测试与三次方程程序通过 |
| 正确性与失败处理 | 已知答案、浮点边界、预算耗尽、无异号、非有限回调 | 33项库与场景测试、16组JS/CLI检查通过 |
| 可复现且边界清楚 | 一条验证命令、工具版本和留存日志、能力限制表 | 已完成；仅验证Windows/JS |
| 学习与反馈 | 至少一名非实现者实际换函数并正确解释两个失败场景 | 待真人试用；已准备流程与空白模板 |
| 赛事认可 | 主办方复核有效提交、范围、材料与MVP | 待重提与复审；不是测试可以替代的结论 |
